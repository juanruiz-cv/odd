# FASE 5 — Movements (EPIC-005)

## Objetivo
Implementar la capa operativa de movimientos de carga: máquina de estados de `CargoStatus` (BR-016), `POST /api/v1/cargos/:id/movements` con observación obligatoria e historial (BR-006/007/008), validaciones de ubicación/capacidad por unidad compatible (BR-003/004/005/033/034/035), transacciones de segmentos `CargoLocation` (BR-039), movimientos parciales y descarga parcial (BR-037/038), reversión ADMIN (BR-012) y alerta de capacidad (BR-033/036 → AlertType.CAPACITY). UI del flujo en frontend (P5-T4).

## Problema
FASE 4 dejó consultas y capacidad derivada, pero ningún write path: no se puede mover una carga, crear/egresar segmentos de distribución ni registrar observaciones de movimiento. `Movement`, `Observation`, `Alert` y `CargoLocation` están modelados en el schema desde F1 pero sin servicio ni endpoints (los write verbs quedaron explícitamente diferidos a F5 en `cargo.controller.ts`).

## Por qué
PHASES.md §9 — Movements (EPIC-005): hitos P5-T1..P5-T8. Es la fase que convierte el sistema de consulta en operativo; Movements consume BR-004/005 (assertCanReceive), BR-033/035 (capacidad calculada) y el único ACTIVE por par de CargoLocation entregados en F4. Fase previa obligatoria para el mapa operativo (F6) y dashboard (F7).

## Scope
- Backend: módulo `src/movements` (máquina de estados pura + movement.service + controller facade bajo `/cargos/:id/movements`), endpoints de segmentos (`POST/PATCH/DELETE /cargos/:id/locations...`), reversión, alerta CAPACITY. Tests unit + e2e.
- Frontend: `ObservationDialog` + `ConfirmDialog` + `MovementTimeline` (P5-T4), captura de cantidad/porcentaje en movimientos parciales (BR-037).
- NO incluye: auto-movimiento (las alertas jamás mueven carga — BR-033 nota / PHASES P5-H8), alerta STALE_30D (job F7), mapa SVG (F6), dashboard (F7), `CargoItem` split (excluido de v1 por MASTER-SPEC §2 punto 5).
