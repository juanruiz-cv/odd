## `/auth/me`: borrado, no arreglado

Decidir esto fue el punto mas delicado de la sesion. Evidencia:

- El handler no tenia `@RequirePermissions` ni era `@Public()`, asi que `PermissionsGuard`
  caia en deny-by-default (`permissions.guard.ts:47-48`) y lanzaba `ForbiddenException`
  **siempre**. Endpoint 100% inalcanzable.
- Sus anotaciones Swagger anunciaban 200/401/403: el contrato publicado mentia.
- Su payload no apportaba nada: `POST /auth/login` y `POST /auth/refresh` ya devuelven el
  mismo snapshot con `roles[]` y `permissions[]` (`auth.controller.ts:82-83`, `:153-154`).
- Ningun llamador lo referenciaba. No aparece en el corpus de docs.
- **El frontend tampoco lo consume**: `grep` sobre `cargoops-frontend/src` → 0 coincidencias
  de `auth/me`, `getMe`, `currentUser`.

**Por que NO se arreglo con `@Public()`**: `IS_PUBLIC_KEY` lo respetan **los dos** guards
(`jwt-auth.guard.ts:43-48` y `permissions.guard.ts:34-40`). Habria pasado a devolver
`req.user` indefinido sin exigir token. Es un retroceso de seguridad.

Las dos vias correctas requieren trabajo de mas: un tercer modo de autorizacion
(autenticado pero sin permiso) o un codigo de permiso concedido a todos los roles.
Ninguna corresponde a un endpoint sin consumidores.

**Verificacion en vivo** (API levantada, Postgres y Redis up):

```
GET /api/v1/auth/me  ->  404   (confirmacion de que el endpoint ya no existe)
```


no tiene bug.

## D-99: access token sobrevive al logout — CONFIRMADO

```
GET /cargos con access token  -> 200
POST /auth/logout             -> 200
GET /cargos con el MISMO token -> 200   <-- sigue sirviendo
```

El access token es stateless y no se invalida. Tras un logout, un access token robado
sigue siendo valido **hasta 900 s (15 min)** desde su emision. Refresh si se revoca, access no.

**Decision previa:** aceptado. Documentalo como riesgo de seguridad conocido si alguna vez
importa. No es un bug de implementacion, es la consecuencia de JWT stateless + TTL de 15 min.
